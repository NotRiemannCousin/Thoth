Detailed Description

Class that makes the HTTP/1.X communication. It transforms "bytes on the wire" into request/response pieces and back. It's just the act of send/receive data, no connection pooling, method resolution, routing, etc.

Note
Reading and writing share the same knowledge about body framing. This is specific to HTTP/1.0 and 1.1.

Reading from the wire

//! ReadRequest(ctx, factory)          ReadResponse(ctx, factory)
//!   ├── ReadRequestHead(ctx)           ├── ReadResponseHead(ctx)
//!   │     └── ReadHeaders(ctx)         │     └── ReadHeaders(ctx)
//!   └── ReadBody(ctx, head, factory)   └── ReadBody(ctx, head, factory)
//!         ├── ReadChunkedBody               (or ReadInto for Content-Length)
//!         │     ├── ReadLine (chunk size)
//!         │     ├── ReadInto (chunk data, pushed through BodyIo::Write)
//!         │     ├── ExpectCrlf (post-data)
//!         │     └── ReadHeaderBlock (trailers)
//!         └── Fill(ctx)  ← the ONLY place in the whole read side that
//!                          co_awaits the transfer source
//!

Every function receives the same ReadContext (source + ExchangeBuffer + HttpLimits). A Recv may deliver more bytes than a stage needs, so leftovers flow to the next stage through the shared window. ReadContext::deadline is the deadline of the current operation.

Some body types needs a preparation stage before start to receive bytes (like opening files or asserting that some headers are specified). So the body factory runs before the first body byte is consumed and the Server can reject a body (factory returning an error) without even draining the stream.

Writing to the wire

//! WriteRequest(socket, request)            WriteResponse(socket, response)
//!   ├── PrepareBodyHeaders (pure)            ├── PrepareBodyHeaders (pure)
//!   ├── WriteRequestHead<S, Method>          ├── WriteResponseHead
//!   │     └── Send (line + headers in        │     └── Send
//!   │         ONE send, formatter-rendered)
//!   └── WriteBody (BodyIo::Read slices,      └── WriteBody
//!       Content-Length or chunked frames + last-chunk)
//!

Sync x Async

This transport engine is designed to work with every { Sync, Async } x { Client, Server } socket with a single interface. Joining sync and async requires both paths to use corroutines because of Send/Recv calls, but the sync one is executed sincronously, the convergence is just to align the signature and implementation.

Note
One minute of silence to the bealty Sync HTTP parser that used RecvStream() (/joke).

Error model

Becuase of how senders/async C++ works, errors are thrown, not returned. A single try/catch at the Client/Server boundary will convert them back into the expected<> world in sync sockets and given that exec::task maps the error channel to std::exception_ptr, you can remap it back to ThothError using let_error. (it's sad but is the price to pay for a single simple implementation):

try { co_return co_await details_::Http1::ReadResponse(ctx, factory); }
catch (const Hermes::TransferError& e) { return std::unexpected{ ThothError{ e.error } }; }
catch (const ThothError& e) { return std::unexpected{ e }; }

Framing rules

As specified by the RFC, while reading Transfer-Encoding: chunked have higher priority. If absent, Content-Length is setted with size 0 (so responses like 204 parse fine) (chunked on HTTP/1.0 is rejected). On the write side the framing comes from BodyIo::Size (a known size uses Content-Length, nullopt uses Transfer-Encoding: chunked). On HTTP/1.0 an unsized outgoing body cannot be chunked, so the caller has to handle that itself (buffer it up to a known size or refuse the exchange).

Request and Method handling

ReadRequestHead returns the raw method as std::string because methods are typed (MethodConcept) and cannot be resolved while reading the wire. Using pair<string, RequestHead> instead of a typed Response is a sad decision but I can live with that. Resolving the method is the Client/Server's job (the Server will forward this decision to the Router).
